# A session at depth: the 27B hybrid on the RTX 5090, 2026-10-11

What one chat turn costs as the context fills, up to the context that fits before compaction. Engines: llama.cpp
(CUDA build ac4cddeb0) and the tinygrad fork (exp f9e245c4e, measured only, not changed). Model
the 27B hybrid, Q4_K_M, qwen35 architecture (16 attention layers, 48 Gated DeltaNet layers). RTX 5090, 32,607 MiB, driver 595.99.02.

    pipeline MODEL --run RUN --target nvidia_sm120 --provider llama.cpp --workload session --ctxs cap,16384 --analyze --measure auto --no-search
    pipeline MODEL --run RUN --target nvidia_sm120 --provider tinygrad --workload session --ctxs 1024,8192 --measure auto --no-search

## The method

- **A turn** is 512 fresh tokens appended to a cache that already holds C tokens. Its time is untraced, from the
  first forward call to the first token. llama.cpp: `llama-bench -p 512 -n 64 -d C -r 3` (its own random ids from
  its fixed seed; the depth is filled untimed). The fork: its own `generate()` keeps the C tokens it holds and
  appends 512 (`runtime/tinygrad_session_profile.py`).
- **Decode** is 64 greedy tokens at that depth, the engine's own timing.
- **Varied tokens.** The reference and the fork read real text: the Python 3.12.3 standard library's top-level
  modules in name order, tokenized by llama.cpp's own tokenizer. 217,980 ids, sha256 aa5a1441...b8f3, saved in the run.
- **Prompt cache off** for every measured request (`cache_prompt: false`). The warm-cache case is its own row.
- **Depths** come from the model's cap: 1K, then x4, then the deepest turn that ends at the binding cap. The next
  depth is decided after the last one is measured, so the cap uses the memory the engine really held.
- **Correctness.** After the turn, the next 17 greedy tokens and the top 5 probabilities at each step. The rule:
  the greedy tokens are equal, the top-5 sets are equal, and no probability differs by more than 0.05.
  llama.cpp is checked against itself: the append path (C cached by the server, the turn appended) against the
  same C + 512 tokens cold, two runs. The fork is checked against llama.cpp's cold run, an independent engine.
- **Clocks and power** from NVML every 50 ms (`gpu_telemetry`). The clock cannot be set without root, so the
  policy is fixed power: the board runs at its own 600 W limit and the clock it chose is logged.

## 1. The caps

The model declares **262,144 tokens** (`qwen35.context_length`). The GGUF has no rope-scaling key, so there is no
extension.

The cache has two parts:

| part | layers | what it holds | size |
|---|---|---|---|
| attention KV, grows with the context | 16 | K and V, 4 kv heads x 256 | 64 KiB per token at f16, 34 KiB at q8_0 |
| Gated DeltaNet state, fixed | 48 | conv window 3 x 10,240 and state 128 x 6,144, f32 | 149.6 MiB at any depth |

The fixed state is confirmed by llama.cpp itself: its server's context checkpoint is 149.626 MiB.

The memory cap is (device less 3%, less what the engine held beside its KV cache) / KV bytes per token.

| KV cache type | memory cap (measured, llama.cpp) | model cap | binds | max context before compaction |
|---|---|---|---|---|
| f16 | 197,660 | 262,144 | **memory** | 197,660 |
| q8_0 | 372,067 | 262,144 | **model** | 262,144 |

Before any depth, from the weights (18.96 GB) and the state alone, the f16 memory cap was 214,316. The measured
fixed part is 18.8 GiB (compute buffers and the output), which lowers it to 197,660. At depth 197,084 the device
held 31,553 of 32,607 MiB. The fork holds more beside its cache (20.8 GiB), so its own f16 cap is 165,911.
llama-bench's default cache is f16, so llama.cpp was measured to 197,084 (the deepest turn inside 197,660).

The fork prefills a hybrid one token at a time, so a 512-token turn costs the same 25.4 s at any depth. Its 8K
fill took 423 s. Its turns run after the check and follow each other (a recurrent state cannot go back), so the
"8,192" turns are at depths 9,744 to 10,768.

Warm cache at the focus depth:
- llama.cpp at 16,384: the same tokens sent again with the cache on computed 4 tokens in 36.6 ms. It restored a
  context checkpoint 4 tokens back and recomputed from there.
- The fork at 8,192: the same tokens sent again computed all 11,344 tokens in 287.2 s. Its prefix reuse does not
  hold for this hybrid after a decode, and it keeps no checkpoints.

## 3. Compaction

A 2,048-token summary re-prefilled on an empty cache:

| engine | summary ms | deepest turn ms | shallow turn ms | the summary costs |
|---|---|---|---|---|
| llama.cpp | 520.5 | 607.3 at 197,084 | 125.1 at 1,024 | 0.9 deep turns; repaid after 1.1 turns |
| tinygrad | 51,522.2 | 25,490.9 at 8,192 | 25,385.8 at 1,024 | 2.0 turns; the fork's turn does not grow with depth |

On llama.cpp, compacting at the cap costs less than one turn there. Every later turn then costs about 125 ms
instead of 607 ms.

## 4. Where the turn goes at depth 16,384 (llama.cpp)

One turn captured with nsys after the depth was filled. It is attributed with the prefill pairing and ceilings
(`prefill.role_time` with the depth), and the KV reads count every key the turn reads. The untraced turn is 143.0 ms.
The captured rows sum to 144.0 ms. MFU over the turn is 24.5%.

| row | path | ms now | ms at ceiling | share of the turn | MFU |
|---|---|---|---|---|---|
| ffn_down + ffn_gate_up Q4_K | int8 | 58.77 | 17.60 | 41% | 29.9% |
| attention (16 layers, after 16,384 keys) | fp16 + fp16_f16acc | 19.01 | 10.03 | 13% | 52.8% |
| gated_delta_net_cuda | no matrix instruction | 18.66 | no ceiling | 13% | |
| attn_qkv + attn_qo Q8_0 | int8 | 11.87 | 3.62 | 8% | 30.5% |
| attn_gate + ssm_out Q8_0 | int8 | 10.12 | 3.11 | 7% | 30.7% |
| mul_mat_q_stream_k_fixup | | 4.08 | 1.14 | 3% | |
| unary_gated_op_kernel | | 3.49 | no ceiling | 2% | |
| rms_norm, quantize q8_1, concat, other small kernels | | 18.0 | | 13% | |

The GEMMs sit near 30% of the int8 peak, as they do in cold prefill. At this depth attention is 13% of the turn.
At 197,084 the turn is 4.2 times longer; the growth is attention reading the cache.

## 5. Throttling

Every llama.cpp row hit the 600 W software power cap: 11% of samples at 1K, rising to 87% at 197,084 (mean clock
2,693 MHz, minimum 2,152, 85 C). The rows are flagged THROTTLED in the table. The fork never reached the cap
(516 W max) and is marked held.

## 6. Suspects

- **The top-5 set rule fails on llama.cpp against itself.** The two runs split the batch differently: cold is one
  C + 512 pass, append is a checkpoint restore and then 512. Greedy tokens agree at 4 of 5 depths, and \|dp\| is
  0.001 to 0.006 at 4K, 65K and 197K. The sets differ only at low-probability ranks. The rule is not loosened here.
  The numbers are reported as they are.
- **Depth 1,024 diverges on both engines** (llama.cpp's self-check at token 9, the fork against llama.cpp at token
  12). The same text at the same place, so the text likely has a near tie there. It is not shown to be a cache bug.
- **\|dp\| 0.105 at 16,384** on llama.cpp's self-check, with all greedy tokens equal. It is larger than at any other
  depth. Not chased.
- **gated_delta_net_cuda has no work model.** BoltBeam counts no operations or bytes for the DeltaNet kernel, so its
  18.7 ms (13% of the turn) has no ceiling. This is a known gap.
- **The fork's warm resend recomputes everything** (287 s for 11,344 tokens). This is the fork's behaviour on a
  hybrid. It is measured, not changed.
- **A driver bug found and fixed in this run**: the fork's session driver sized the model for one turn. The later
  turns went past `max_context` and `generate()` yielded nothing. The first fork run failed both depths with
  StopIteration. The fix sizes the context for every turn.
