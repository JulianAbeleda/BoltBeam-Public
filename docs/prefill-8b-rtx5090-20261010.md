# Prefill measured faithfully: Qwen3-8B on the RTX 5090, 2026-10-10

What a prompt costs, against what it could cost, per kernel. Engines: llama.cpp (CUDA build 50569eb8) and the
tinygrad fork (exp caf6ca7af). Model Qwen3-8B-Q4_K_M. RTX 5090, driver 595.99.02, CUDA 13.2.

## The method

1. **Measured peaks per path** (`collectors/cuda_compute.py`). One PTX `mma.sync` instruction per path in a
   register loop through the CUDA bridge. The best launch shape runs back to back for 2 to 3 s. The figure is the
   median launch of the second half (the plateau), at the mean SM clock over that half (NVML, `gpu_telemetry.py`).
2. **Truth** (`collectors/prefill.py`, step 4). The untraced prefill at the engine's own chunk. llama.cpp is
   `llama-bench -p N -n 0`. The fork is `generate()` from its first forward call to the first token. What each
   engine batched is read from the engine itself.
3. **Attribution and tie-out** (step 5). nsys for llama.cpp. The fork's own GPU timestamps for tinygrad, since
   CUDA's tools cannot see it. Each kernel's matrix path is read from its code: PTX in the engine's library, or the
   program's source (`instruction_path.py`). Kernels are paired with roles by launch counts and operations, not by
   bytes or grid (`prefill_attribution.py`). Each row's ceiling is max(operations / its path's peak,
   bytes / bandwidth). The table uses the decode table's own ranking and cells (`tie_out.where_prefill_goes`).
4. **Curve** (`workflow/prefill.curve`). Every length of a run and its sibling runs, in the HTML report and the
   text summary.

Clock policy: **fixed power**. The clock cannot be set without root (`nvidia-smi -rgc` is refused). The board
runs at its own 600 W limit and the clock it chose is logged.

Every path reaches 99.5 to 99.8% of its architectural rate per clock. The spec is lower only because of its clock.

are superseded. The fp16-accumulate and fp4 runs had NVML's software power cap set at 545 and 583 W with the clock
held at 2,872 MHz.

| engine | prompt | prefill ms (3 reps) | tok/s | chunk | throttled |
|---|---|---|---|---|---|
| llama.cpp | 512 | 34.6 (41.4 first) | 14,807 | ubatch 512, batch 2048 | no |
| llama.cpp | 2,048 | 141.6 | 14,464 | 4 x 512 | no (cap set, clock held) |
| llama.cpp | 8,192 | 631.4 | 12,974 | 16 x 512 | **yes**: power cap in 46% of samples, 607 W peak |
| llama.cpp | 32,768 | 3,622.2 | 9,047 | 64 x 512 | **yes**: power cap in 84% of samples, 515 W mean |
| tinygrad | 512 | 61.4 (graph replayed) | 8,341 | 1 x 512 | no |
| tinygrad | 2,048 and up | not measured | | | fork out of GPU memory |

Both engines batch the prompt. Neither prefills token at a time.

The fork has two findings:

- **Eager re-scheduling.** By default (no workload reuse) the fork schedules its graph again for every
  independent prompt. That is 13.5 s of host time for a 512-token prompt against 47 ms of GPU time. The first
  eager prompt took 29.1 s and the capture took 15.0 s. The 61.4 ms above is the replayed graph.
- **Out of memory from 2K up.** At 2,048 tokens the fork runs out of GPU memory: "Allocation of 2.50 MB failed,
  Used: 29.50 GB". This happens with the graph replayed and in its own default eager mode, run directly outside
  BoltBeam too. The fork has no 2K, 8K or 32K point.

## 3b. Where the prefill time goes, tinygrad, at 512 (its only length)

61.4 ms untraced. The ceiling sum is 5.6 ms. The gaps row is 13.9 ms of kernel launches, as the fork's own timing
is the untraced prefill less the busy time. Paired: ffn_gate_up Q4_K 15.14 ms (24.6% MFU) and attn_qo Q4_K 6.42 ms
(19.3%). Not paired: q4_down_streamk (4.74 ms), nv_q6_oracle (4.08 ms, its source is a stub so its path is
unknown), r_8_32_32 (3.38 ms) and E_4_8_32 (2.20 ms). Five assignments fit equally by counts and operations: the
k/v and down projections of two formats have equal counts and shapes. Only the agreed part is kept. The fork
attaches role metadata to 1 of its 45 prefill programs, which is why it does not name them itself.

For comparison, llama.cpp at 512 takes 34.6 ms.

## 4. The curve, llama.cpp

| prompt | ms | MFU | attention ms (MFU) | ffn Q4_K ms (MFU) | attn_qo ms (MFU) |
|---|---|---|---|---|---|
| 512 | 34.6 | 21.1% | 1.65 (19%) | 14.82 (31%) | 4.35 (29%) |
| 2,048 | 141.6 | 23.2% | 10.69 (46%) | 59.56 (31%) | 17.70 (28%) |
| 8,192 | 631.4 | 30.2% | 103.76 (76%) | 247.07 (29%) | 73.53 (27%) |
| 32,768 | 3,622.2 | 47.1% | 1,504.75 (84%) | 998.82 (29%) | 303.41 (26%) |

The GEMMs hold flat at 22 to 31% of the int8 peak at every length. This matches the 2026-09-23 ncu finding that
mul_mat_q is load-store bound. Attention grows quadratically and its MFU rises to 84% of the fp16 peak. That MFU
is on the slower of its two paths, so it is an upper bound. The whole-prefill MFU rises with length only because
attention takes over.

## Suspects

- **Mixed-path attention.** `flash_attn_ext_f16` issues both fp16 and fp16-accumulate mma. Its ceiling uses the
  slower peak, so attention's lost time is a lower bound and its MFU an upper bound.
- **Throttling at 8K and 32K.** The board reached its 600 W cap and the clock dropped (mean 2,248 and 2,544 MHz
  against 2,947 MHz). Those points are fixed-power numbers, flagged.
- **Telemetry window.** It includes llama-bench's own warm-up and model load; idle samples are dropped.
- **Stub sources.** A fork program whose source is a stub has no readable path. nvdisasm on the program binary
  would read it; nvdisasm is not on this box's toolkit.
- **Activation bytes.** These are counted at 2 bytes per element. llama.cpp reads q8_1 (1.125) and writes fp32.
  The bytes side never binds the GEMMs here.
- **Same-format splits.** Pairing assumes a template reads one weight format. True for llama.cpp's mmq and mmvq.
  For the fork, roles of different formats sharing counts stay unpaired.
- **The fork's eager default.** Without workload reuse, the fork's first-token time is dominated by
  re-scheduling (13.5 s at 512). The replayed number is the GPU's capability, not what a user's first prompt sees.

## Not generic, listed

- `cuda_compute.py`, `gpu_telemetry.py` (NVML) and `instruction_path.py` (PTX, cuobjdump) are NVIDIA-vendor
  adapters, the same category as `cuda_bandwidth.py` and `vendor_capture.py`. Another vendor needs its own row.
- `collectors/prefill.py ENGINES` names llama.cpp and the tinygrad fork. Each is an engine adapter, as in
  `providers.py`.
- `runtime/tinygrad_prefill_profile.py` sets the fork's `prefill_workload_reuse` to replay the prefill. That is a
  fork config field.
- Attention is found by kind words (`tie_out.kind_of`), the decode table's existing rule.
- Shapes, models and chip names are in no code. All counts and shapes come from the model profile.
